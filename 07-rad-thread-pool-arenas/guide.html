RAD linker thread-pool arenas in Rust

An arena is not thread-safe, so a parallel job gives each worker thread its own arena. The RAD linker bundles those into a TP_Arena and saves and restores all of them together. In Rust, scoped threads and &mut borrows make "one arena per thread" a guarantee instead of a convention.

1. The idea

Pushing onto an arena moves its position without a lock. Two threads pushing onto the same arena at once would hand out overlapping memory. Adding a lock would make every allocation contend. The RAD linker's answer is to give each worker its own arena:

 main thread:   TP_Arena { v = [arena0, arena1, arena2] }
                TP_Temp t = tp_temp_begin(arenas)       save pos of all three
                tp_for_parallel(pool, arenas, 7 tasks)
 worker 0:        tasks 0, 3, 6  → push results onto arena0
 worker 1:        tasks 1, 4     → push results onto arena1
 worker 2:        tasks 2, 5     → push results onto arena2
 main thread:   read every task's result (they point into the three arenas)
                tp_temp_end(t)                          pop all three back

No locks, no contention, and the results live until the main thread decides they are no longer needed.

2. The C version

Creating the set allocates one arena per worker, then stores the array of pointers inside the first arena.

Saving and restoring positions loops over every arena. The array of saved positions is itself pushed onto arena 0, which is why tp_temp_end restores arenas 1..n in its loop and relies on the order for arena 0.

Arena 0 is not popped. tp_temp_end's loop stops at index 1, so arena 0 keeps everything pushed during the scope (including the saved positions array). That may be deliberate, since the positions live there, but it means temp scopes leak into arena 0 until it is released.

Nothing in C checks that a task only touches its own worker's arena. The task function receives the worker index and is trusted to use it.

3. The Rust version

Running tasks in parallel

for_parallel starts one scoped thread per arena and hands it &mut that arena via iter_mut(). The compiler knows each &mut is unique, so two threads can never share an arena. Task i runs on worker i % workers, and the results come back in task order.

Three type-level facts carry the safety argument:

  • Arena: Send, so an arena (or &mut to one) may move to a worker thread.
  • Arena: !Sync, so &Arena cannot be shared between threads. A task cannot smuggle its arena to another thread.
  • Results borrow 'a, the lifetime of &'a mut self. Results such as &[T] pointing into worker arenas keep those arenas borrowed, so they cannot be popped while the results are alive.

Saving and restoring all positions

All arenas, including the first, are popped. The saved positions live in an ordinary Vec, not in an arena.

The real cost of this port is the thread spawn per worker per job. A persistent pool would avoid it; the safety argument would be the same as long as the pool hands each worker &mut its own arena for the duration of a job.

5. How to use it

Seven "object files" are parsed by three workers; worker 0 got three tasks and the others two, which matches the positions shown. After the scope, every arena is back at 128 bytes, just its header.

6. Building it yourself, step by step

  1. Make the arena Send but not Sync. That is the honest description of a lock-free bump allocator.
  2. Keep one arena per worker in a Vec.
  3. Hand them out with iter_mut() inside std::thread::scope, so each thread gets a unique borrow and all threads finish before the scope returns.
  4. Tie results to the borrow by giving the task closure &'a Arena and returning Vec<R> from a method taking &'a mut self.
  5. Add a group temp that saves every position and pops them all in Drop.
  6. Test result order, task-to-worker mapping, that the temp restores every arena, and more workers than tasks.
