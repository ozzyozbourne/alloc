C allocators in Rust

Seven custom allocators from the Kohi game engine and the RAD Debugger, rebuilt on Rust's std::alloc::Allocator trait (stable from Rust 1.100). Each folder has the Rust crate, the original C it copies, tests, a runnable example, and a guide comparing the two.

2. The trait in one minute

Everything in this repository implements, or is built on, this trait. Only two methods are required:

RuleWhat it means for your allocator
&self, not &mut selfMany containers share one allocator, so state changes need Cell, RefCell or a Mutex.
Layout in and outYou always get the size and alignment, including on free. C allocators usually have to store the size themselves.
NonNull<[u8]>Pointer plus the real size you handed out, which may be larger than requested.
unsafe traitCollections trust you: blocks never overlap and stay valid until deallocated, the allocator is dropped, or it is mutated through &mut.
No unwindingAllocator methods must not panic. Return AllocError, or abort for corruption.
&A: AllocatorPass &my_alloc to Vec::new_in / Box::new_in. The borrow then stops you from resetting or dropping the allocator while those containers live.

That last rule is the main thing Rust adds over C. In every C allocator here, resetting or destroying the allocator while pointers into it are still in use compiles fine. In the Rust ports, it is a compile error, without any runtime cost.

3. What is stable in 1.100

  • Stable: the Allocator trait, AllocError, Global, System: Allocator, Box::new_in, Box::from_raw_in, Box::into_raw_with_allocator, Vec::new_in, Vec::with_capacity_in, Vec::allocator.
  • Still unstable (allocator_ext, #163177): Rc/Arc/VecDeque/BTreeMap with allocators, Box::try_new_in, Box::new_uninit_slice_in. String and HashMap take no allocator parameter.

The repository pins the beta toolchain in rust-toolchain.toml until 1.100.0 reaches stable (expected 2026-11-12). Nothing here uses #![feature].
