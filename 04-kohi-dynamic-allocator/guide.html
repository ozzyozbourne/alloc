Kohi dynamic allocator in Rust

Kohi's general-purpose heap: a freelist over one big block, with per-allocation headers, memory tags for usage reports, debug guard bytes, and a mutex. Every kallocate in the engine goes through it. The Rust port does all of that, and can also be the Rust program's #[global_allocator].

1. The idea

At startup Kohi asks the OS for one large block. From then on, every allocation in the engine is carved out of that block by a freelist. The engine gets three things a plain malloc does not give it:

  • A memory budget. The engine cannot use more than the block.
  • Usage by subsystem. Every allocation carries a tag (MEMORY_TAG_TEXTURE, MEMORY_TAG_GAME, …), and the memory system keeps a byte count per tag.
  • Debugging. In debug builds each allocation records the file and line that made it, and guard bytes around the data catch writes past either end.

Each allocation takes more bytes from the freelist than the user asked for:

 C (Kohi):    [ padding ][ u32 size ][ guard ][   user data   ][ guard ][ alloc_header: start, align, tag, file, line ]
                                              ^ returned pointer

 Rust port:   [ padding ][ Header: start, tag, site ][ guard ][   user data   ][ guard ]
                                                              ^ returned pointer

Why the difference? kfree(ptr) receives only a pointer, so C must store the size right before the data to find everything else. Rust's Allocator::deallocate(ptr, layout) always receives the size and alignment, so the Rust header does not need to store them.

2. The C version

The header

Creating it

The block is laid out as [state][freelist nodes][user memory]. As with the freelist, you call create once to learn the size and again with memory.

Allocating

It always asks the freelist for alignment + header + 4 + size (plus guards), enough for the worst-case padding, then places the user block inside that range.

Freeing

From the pointer alone it reads the stored size, finds the header after the data, recomputes the same required_size, and gives the range back.

The memory system on top

kmemory.c wraps the allocator in a mutex, keeps the per-tag statistics, and zeroes every allocation. kallocate(size, tag) is a macro that adds __FILE__ and __LINE__.

3. Notes on the C version

Shutdown uses freed memory. memory_system_shutdown destroys the mutex and frees the whole block (which contains the mutex), then calls kmutex_unlock(&state_ptr->allocation_mutex) after the if.
4 GiB limit. The size is stored in a u32, so allocations are capped by an assertion.
Off-by-one range check. dynamic_allocator_free_aligned rejects block > memory_block + total_size, so a pointer exactly at the end passes. get_size_alignment uses >=.
Every kallocate zeroes the memory it returns. Rust leaves that choice to the caller: allocate does not zero, allocate_zeroed does.

4. The Rust version

Tags and the header

Instead of C's 256-byte file name buffer, the header stores a &'static Location, which is one pointer to the file, line and column the compiler already embeds in the binary.

How big a range an allocation needs

This function is the contract between allocate and deallocate: it depends only on the Layout, so freeing computes exactly the number allocation used. If the two ever disagreed, the freelist would leak or double-free; the test freeing_everything_in_any_order_restores_all_free_space checks they agree.

The allocator and its block

The freelist's nodes live inside the managed block, like C. RawNodes is the storage type that points there, and the whole mutable state sits behind a Mutex, so the allocator is Sync and threads can share it.

Allocating

Take a range from the freelist, align the user pointer inside it, write the header in front and the guards on both sides, and update the stats, all under the lock.

Freeing

Check the guards, read the header for the range's start and tag, recompute required_size from the layout, and give the range back. If the freelist rejects it (a double free, for example), the allocator aborts, matching C's KFATAL.

Tags: a handle instead of a parameter

Allocator::allocate has no room for a tag argument. So heap.tagged(MemoryTag::Game) returns a small Copy handle that remembers the tag and, through #[track_caller], the source location of the tagged call. That handle is itself an Allocator: Vec::new_in(heap.tagged(MemoryTag::Game)) tags every buffer that vector allocates.

As the global allocator

Kohi routes the whole engine through this heap. GlobalHeap<N> does the same for a Rust program: it is a static holding an N-byte buffer, builds the allocator inside it on first use, and implements GlobalAlloc. This only works because the allocator never allocates anywhere else; a Box<[Node]> for the freelist would call the global allocator from inside the global allocator.

6. How to use it

As an allocator you pass around

The last part shows fragmentation, the main weakness of a freelist heap: after freeing every other block, half the heap is free, but no single hole is big enough for a 4 KB request. Once everything is freed, the ranges merge back into one and all 1,048,576 bytes are free again.

As the global allocator

Even the HashMap, the thread spawn and std's own start-up allocations land in the Kohi heap. They are tagged UNKNOWN, because GlobalAlloc has no way to pass a tag.

7. Building it yourself, step by step

  1. Start from a range allocator (folder 03) that hands out offsets.
  2. Write a pure function from Layout to range size, including headers, guards and worst-case alignment padding. Use it in both allocate and deallocate.
  3. Lay out each allocation: align the user pointer inside the range and put a header where you can find it from the user pointer. Store the range's start, because the user pointer is not at the start.
  4. Lock. An allocator shared by threads must be Sync; wrap the freelist in a Mutex and keep the critical section short.
  5. Never panic in allocator methods. Return AllocError for "no memory"; abort for corruption.
  6. For a global allocator, make sure nothing inside allocates through the global allocator, including the node storage and lazy initialization.
  7. Test random allocate/free sequences that end with "everything freed means all space is free", alignment up to a page, threads, and a deliberate overrun that the guards must catch.
