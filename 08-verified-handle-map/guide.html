A verified handle map in Rust

A handle map that is its own allocator: it owns a fixed array of slots and decides which are in use. Because it is small and fixed in size, Kani can prove it correct for every reachable state at capacity 4. This page compares it with Odin's core:container/handle_map and the slotmap crate, and shows exactly what the proofs cover and what they don't.

1. The idea

A handle map stores values in slots and hands out handles: a slot index plus a generation. Removing a value changes the slot's generation, so every old handle to it stops resolving, even after the slot is reused for something else. Games use this for entity references: system A can remove an enemy and spawn a pickup in the same slot, and system B's stale handle to the enemy just returns None, instead of silently pointing at the pickup.

 slots:       0           1           2           3
 occupied:   yes          no         yes          no
 generation:  1           2           1           0
 value:     player       ---        camera       ---
 free list:  head → 1 → 3 → end

 add(pickup):  take slot 1, generation 2 → 3, return Handle { idx: 1, generation: 3 }
 get(Handle { idx: 1, generation: 2 }):  slot 1 has generation 3 → None   (stale)

The map manages its own slot memory with MaybeUninit<T>. That is the unsafe part, and it is what the proofs are mostly about: a slot must be read only when it holds a value, moved out exactly once, and dropped exactly once.

Rust: slotmap::SlotMap

slotmap stores Vec<Slot<T>>, where each slot is a union of the value and the next free index, plus a u32 version. An odd version means occupied, even means vacant, so occupancy costs no extra memory. Removing does version.wrapping_add(1).

3. This implementation

Layout

Parallel arrays like Odin, MaybeUninit<T> like slotmap's ManuallyDrop. Two choices differ from both:

  • A separate occupied flag. slotmap's odd/even trick saves a byte per slot, but it makes the generation do two jobs. Keeping them apart lets every generation only ever increase, which is a property the proofs check.
  • Generations never wrap. A slot whose generation reaches G::MAX is retired: emptied and never put back on the free list. Odin and slotmap wrap instead (section 5).

The generation type

The generation is a type parameter, so the same code can be checked with u8, where the retirement path is reached after 255 reuses, and used with u32 or u64 in practice.

4. The proofs

How they avoid running out of memory

The first attempt in this project simulated random sequences of operations from an empty map. Each extra step multiplies the work for the solver, and 4 steps on 3 slots already used more than 3 GB. The fix is induction:

  1. Base case: new() satisfies check_invariant (new_map_is_valid).
  2. Step: start from an arbitrary map that satisfies the invariant, any occupancy, generations, free list and values, run one operation with arbitrary arguments, and check that the invariant still holds and the result is right.

Since every operation keeps the invariant, it holds after any number of operations, and the per-operation checks hold in every reachable state. The bound is the capacity (N = 4), not the number of steps. Kani also checks every unsafe block on every path: no read of an empty slot, no out-of-bounds index, no overflow.

5. The wraparound bug in Odin and slotmap

Both increment a slot's generation with a wrapping add. After enough reuses of one slot, the counter comes back to a value an old handle still holds, and that stale handle resolves again, to whatever now lives in the slot.

  • slotmap uses a 32-bit version that advances by 2 per reuse, so one slot must be reused about 2.1 billion times. Rare, but a hot slot in a long-running server can get there.
  • Odin lets you pick the handle type. With its Handle16 (u8 generation), one slot reused 256 times revives every handle from its first use. With Handle32 it is 65,536 reuses: about 18 minutes of reusing one slot every frame at 60 fps.

The naive-generations feature switches this crate to the wrapping behaviour. Kani then finds the bug in add_is_correct ("add reissued an old generation", in the results above). With u8 generations a wrap can also give an occupied slot generation 0, which breaks the invariant, and the model test fails at step 8,004. Retiring the slot instead costs one slot per 255 (or 4 billion) reuses of it.

6. Tests beside the proofs

The proofs cover capacity 4. Ordinary tests cover larger maps and long runs:

  • Model test: 20,000 random operations on 16 slots with u8 generations, compared after every step with a HashMap<Handle, T>, with stale handles checked and the invariant asserted. Slots do retire during the run.
  • Differential test: the same 10,000 operations on this map and on slotmap::SlotMap; values and liveness of every handle, live or stale, must agree.
  • Miri runs all the tests (with smaller counts) and finds no undefined behaviour.

8. What is not proved

  • Capacities above 4. The code has no size-dependent branches, so a bug that needs more slots is unlikely, but it is not excluded. The model test covers 16. 09 proves the bookkeeping for any capacity with Verus.
  • Values are u8 in most harnesses (Counted in the drop one). Value type doesn't affect the bookkeeping, and the map never inspects values.
  • Panics in T's destructor during Drop are not modelled.
  • clear is built from iter and remove, which are proved, but it has no harness of its own.
  • The proofs check this Rust code with Kani's model of Rust semantics. They say nothing about the compiler or hardware.
