Kohi pool allocator in Rust

A pool splits one block into equal-sized slots and hands them out one at a time. Kohi added this allocator on 2026-10-28 and it is not finished yet; the Rust port fills in what is missing and shows the Rust type system catching two of its bugs.

1. The idea

When you allocate and free many objects of the same size, such as particles, entities or network packets, a general-purpose heap wastes time searching and fragments memory. A pool avoids both: every slot is the same size, so any free slot fits any request, and the free slots are kept in a list.

 slots:  ┌────────┬────────┬────────┬────────┬────────┐
         │ slot 0 │ slot 1 │ slot 2 │ slot 3 │ slot 4 │     element_size bytes each
         │  used  │  free  │  used  │  free  │  free  │
         └────────┴────────┴────────┴────────┴────────┘
 free list (sorted by address):  head → 1 → 3 → 4 → end

 allocate():  take head (slot 1),        head = 3              O(1)
 free(2):     walk to the right place,   1 → 2 → 3 → 4         O(free slots)

Kohi keeps the free list sorted by address, so allocation always returns the lowest free slot. That keeps live objects packed toward the start of the block, which is friendlier to the cache, at the cost of an O(n) free. The Rust port keeps the same policy so the two behave the same.

2. The C version

The free list nodes live in a separate array, one node per slot. Each node stores its slot's byte offset and a next pointer.

Creating the pool allocates the slots and the node array, then links every node to the next.

Allocating pops the head and returns the slot's index as well as its address.

Freeing finds the node for the slot and inserts it in offset order.

3. Problems in the C version

Leak. pool_allocator_destroy is empty, so the slot block and the node array are never freed.
Full pool. When every slot is taken, head is null. KASSERT_DEBUG(head) catches that in debug builds; in release builds the next line reads head->offset through a null pointer.
Double free makes a cycle. If a slot is freed twice, the search loop stops at that slot's node (its offset is not less than itself), then sets freed->next = *cur, which is freed. The node now points to itself, and pool_allocator_elements_free loops forever.
Alignment is left to the caller. The block comes from kallocate without an alignment, and slots are element_size apart. Whether each slot is aligned for the element type depends on the size you pass and on the allocator underneath.

4. The Rust version

The struct

Instead of an array of nodes holding pointers to each other, the Rust version keeps an array of indices: next[i] is the free slot after slot i. Indices avoid self-referential pointers, which matters in Rust because the struct is moved when it is returned from new. (C has the same move, but its nodes point into a separate heap array, so it gets away with it.) Each index is a Cell because allocate only gets &self.

Creating it

It takes a Layout rather than a byte size, so slots are sized and aligned for the element type. pad_to_align rounds the slot size up so that every slot, not just the first, is aligned.

Taking a slot

The same O(1) pop. A full pool returns None instead of dereferencing null.

Implementing Allocator

allocate refuses layouts that do not fit a slot, then pops a slot. It reports the whole slot as the block's size, which the trait allows: a Vec could use the extra bytes as capacity.

deallocate is the sorted insert from C. Because it walks the list with indices, it can see when the slot is already in the list and abort, instead of making a cycle. It aborts rather than panics because allocator methods must not unwind.

Destroying it

The compiler also guarantees the order. A Box<T, &PoolAllocator> borrows the pool, so the pool cannot be dropped while any box is alive.

Trying to allocate

Box::try_new_in, which would return an error instead of aborting when the pool is full, is still unstable (it is part of the allocator_ext feature). try_box does the same with stable APIs: it calls allocate, writes the value, and wraps the slot with Box::from_raw_in.

6. How to use it

The demo spawns six particles into four slots; two are refused. Killing particles 1 and 3 frees slots 1 and 3, and the next two spawns reuse them lowest first, because the free list is sorted.

Use Box<T, &PoolAllocator> for single objects. A Vec in a pool only works while its whole buffer fits in one slot, which is rarely what you want.

7. Building it yourself, step by step

  1. Size the slot with Layout::pad_to_align() so consecutive slots stay aligned, and allocate slot.size() * capacity bytes with the slot's alignment.
  2. Build the free list. Either store a next-index per slot in a side array (this port, and Kohi), or store the next pointer inside each free slot (an intrusive list, which needs no extra memory but requires slots at least pointer-sized).
  3. Write allocate: reject layouts larger or more aligned than a slot, pop the head, return the slot.
  4. Write deallocate: compute the index from the pointer, verify it is a slot boundary, and push it back. LIFO push is O(1); a sorted insert, as here, keeps allocations low.
  5. Free the block in Drop with the same layout you allocated it with.
  6. Test order of reuse, exhaustion, alignment of an over-aligned type such as #[repr(align(64))], and rejection of interior or foreign pointers.

8. Tests

The key test frees slot 0 and then slot 2, and checks that slot 0 is handed out first. A LIFO free list, the usual simpler choice, would return slot 2 and fail it.
