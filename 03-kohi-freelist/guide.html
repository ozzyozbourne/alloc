Kohi freelist in Rust

The freelist is the engine inside Kohi's dynamic allocator. It tracks which byte ranges of a region are free, and never touches the region itself. This page ports it and explains why, in Rust, it is deliberately not an Allocator.

1. The idea

A freelist answers two questions about a region of total_size bytes: "give me n free bytes" and "these n bytes at offset o are free again". It answers with offsets, not pointers. That is why Kohi can use the same code for its CPU heap (folder 04) and for sub-allocating Vulkan buffers, whose memory the CPU cannot dereference.

 region:   0          100      150               300                           1000
           ├── used ───┼─ free ─┼────── used ──────┼─────────── free ─────────────┤

 free list (sorted by offset):   (100, 50) → (300, 700)

 allocate_block(30):    first fit → front of (100, 50) → returns 100;   list: (130, 20) → (300, 700)
 free_block(150, 150):  touches 130+20 = 150 on the left and 300 on the right → merges:   (130, 870)

Three rules make it work:

  • Sorted by offset, so neighbours are adjacent in the list.
  • First fit: allocation takes the front of the first range that is big enough.
  • Coalescing: a freed range merges with the free range before it, after it, or both, so the list never holds two touching ranges.

The list nodes come from a fixed array, so the freelist itself never allocates. You ask how much memory it needs, provide that memory, and it lives there. This is what lets the dynamic allocator run as the program's global allocator.

2. The C version

Creating it uses Kohi's two-call pattern: call once with memory = 0 to learn how many bytes the node array needs, then again with a block of that size.

Allocation walks the list and either removes an exact fit or shrinks a larger range from the front.

Freeing is the long part, with cases for an empty list, appending to the left neighbour, inserting before a node and merging both ways, and appending at the end.

3. Problems in the C version

Out of nodes. get_node returns 0 when every node is used, and every caller writes new_node->offset straight away. Heavy fragmentation therefore crashes. The node count is total_size / (sizeof(void*) * sizeof(freelist_node)), at least 20: 21 nodes for a 4 KiB region.
Partial double frees. Only an exact repeat (node->offset == offset) is detected. Freeing a range that overlaps a free range at a different offset, or freeing with the wrong size, silently corrupts the list.
No range check. Freeing beyond total_size is accepted.

4. The Rust version

Nodes and storage

Nodes link by u32 index instead of pointer, and an unused node has size == 0, as in C. The storage is a type parameter S: a Box<[Node]> by default, or any &mut [Node]. That replaces C's two-call pattern with something the type system checks, and folder 04 uses it to keep the nodes inside the heap's own block.

Allocating

A line-for-line match of the C first-fit loop.

Freeing

The C version handles each list shape separately. The Rust version finds the two neighbours once (prev, the last free range starting before offset, and cur, the first one after), rejects any overlap with either, and then a single match on "touches prev?" and "touches next?" covers all four cases. Every error is checked before anything is changed, so a rejected free leaves the list intact.

Resizing

C's freelist_resize hands the old block back through an out-parameter for the caller to free. In Rust, resize consumes the list and returns the old storage, so the caller can decide what to do with it and cannot keep using the old list.

5. Why it is not an Allocator

Allocator::allocate must return a pointer to memory that the allocator guarantees is valid. A freelist only knows numbers; the region might be GPU memory, a file, or not exist yet. Making it an Allocator would force it to own a CPU block, which would remove the GPU use case. So it stays a plain data structure, and folder 04 wraps it, together with a block of memory, into an Allocator. This split (bookkeeping vs memory) is a useful pattern for any allocator.

8. Building it yourself, step by step

  1. Decide on offsets or pointers. Offsets keep the structure reusable for memory you cannot touch.
  2. Pick a node store. A fixed array with a "free" marker (this port), a separate free stack of node indices (faster than a scan), or nodes stored inside the free memory itself (no extra memory, but only for CPU memory).
  3. Allocate: walk the sorted list, take the first range big enough, remove it on an exact fit, otherwise shrink it.
  4. Free: find the neighbours, validate, then merge left, right, both, or insert.
  5. Test against a simple model. A byte map that marks each byte used or free is slow but obviously correct. Run thousands of random operations and compare after each one.

9. Tests

The model test runs 5,000 random allocations and frees on a 4 KiB region and, after every step, checks that the free ranges are exactly the free bytes of a byte map, sorted, disjoint and fully merged. It also checks that a failed allocation really had no fitting range.
