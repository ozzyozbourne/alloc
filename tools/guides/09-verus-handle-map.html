A handle map proved with Verus

The handle map from 08, proved correct for every capacity and every allocator with Verus. Kani explored every state of a 4-slot map. Verus instead checks a written proof, so the size of the map does not matter. This page shows how the proof is built, what it proves, and how it compares with the Kani approach.

1. Why a second proof

Kani is a model checker: it turns the code into one large logic formula and lets a SAT solver search every possible input. That needs no proof writing, but the formula grows with the data, so 08 had to fix the capacity at 4. A bug that needs 5 slots would not be found.

Verus is a deductive verifier. You write the specification next to the code: requires (preconditions), ensures (postconditions), loop invariants, and a spec fn that says what a well-formed map is. Verus then asks the Z3 SMT solver to check each function on its own, against those specs. Nothing is unrolled, so a map with a million slots is covered by the same proof as one with four.

So the two complement each other: 08 keeps the unsafe version checked by Kani and Miri, and 09 proves the bookkeeping for any size.

2. The data structure

The design is 08's: index-plus-generation handles, generations that only increase, slots retired at MAX_GEN instead of wrapping, and an intrusive free list through next_free. Three things changed so Verus can reason about it:

  • Slots are a Vec<Slot<T>, A> from any A: Allocator, created with Vec::with_capacity_in, instead of an inline array. The capacity is a run-time value.
  • A slot's value is an Option<T>, so occupancy is value.is_some() rather than MaybeUninit<T> plus a flag. All code is safe Rust.
  • The generation is a fixed u32.

The four Ghost fields exist only for the proof and are erased when compiling. free_list is the free list as a mathematical sequence; issued and dead record every handle ever returned by add or removed by remove. With them, "a removed handle never comes back" becomes a statement about a set, which the solver can check.

3. The specification

What callers see

Callers reason with a few spec fns, never with the fields. closed hides the body outside the module, so a client's proof depends only on these names and the operations' ensures:

{{rs-item src/handle_map.rs pub open spec fn live(}} {{rs-item src/handle_map.rs pub open spec fn is_reusable(}}

The invariant

wf plays the role of 08's check_invariant, but it is logic, not code, so it can say "for all slots" with no loop. It is split in three, each marked #[verifier::opaque]:

{{rs-item src/handle_map.rs pub closed spec fn wf(}} {{rs-item src/handle_map.rs closed spec fn wf_free(}} {{rs-item src/handle_map.rs closed spec fn wf_count(}} {{rs-item src/handle_map.rs closed spec fn wf_handles(}}

The key part is the last clause of wf_free: each slot on the ghost list links, through its runtime next_free, to the next one, and the last links to NONE. Together with no_duplicates, that means following the real pointers from free_head visits exactly the ghost sequence and stops. No cycle is possible.

The first version had one big wf. Z3 hit its resource limit on add and remove, because every quantifier in the invariant was visible in every step of the proof. Making the parts opaque and revealing only the one each step needs brought the whole file down to about 3 seconds.

4. Operations and their contracts

add

The ensures clause is the contract: on success the handle resolves to the value, was never issued before, and no other handle changed; on failure every slot is occupied or retired and the map is untouched.

{{rs-item src/handle_map.rs pub fn add(}}

The executable part is eight lines: pop free_head, bump the generation, store the value. Everything inside proof { } is hints for the solver. Most say which list element moved where (nfl[k] == fl[k + 1]), so the solver can match the old free list to the new one.

Overflow is proved, not assumed: generation + 1 is safe because the slot is on the free list, so it is reusable, so its generation is below MAX_GEN. Change it to wrapping_add and drop the retirement check (what slotmap and Odin do) and Verus rejects the code (section 6).

remove

{{rs-item src/handle_map.rs pub fn remove(}}

If the slot's generation is MAX_GEN, it is not pushed back: the slot is retired. The ghost list follows the same branch, so wf_free holds either way.

get and new_in

{{rs-item src/handle_map.rs pub fn get(}} {{rs-item src/handle_map.rs pub fn new_in(}}

new_in needs a loop invariant: after i pushes, slots 0..i are empty, have generation 0 and link to j + 1 (or NONE for the last). That is what makes the free list correct for any capacity.

7. What is not proved

  • The unsafe version. This map uses Option<T>. 08's MaybeUninit<T> code is checked by Kani (capacity 4) and Miri, not by Verus. Proving it would mean Verus's PointsTo permission types instead of plain fields.
  • The allocator itself. A is trusted to behave as the Allocator trait promises. vstd's spec for Vec::with_capacity_in and push is assumed, not proved.
  • Trusted base. Verus, Z3, vstd's specs of Vec and Option, and rustc.
  • Fewer operations than 08. No get_mut, iter, clear or generic generation type; adding them is more of the same proof work.
  • Panics on allocation failure. new_in calls Vec::with_capacity_in, which aborts if the allocator fails; that is outside the spec.

8. Running it

This folder is not in the Cargo workspace, because Verus brings its own compiler (Rust 1.99, so #![feature(allocator_api)] is still needed there).
