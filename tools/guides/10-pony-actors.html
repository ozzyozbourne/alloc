Pony's actor allocators in Rust

Pony gives every actor a private heap and passes objects between actors by reference, without copying and without locks. This crate rebuilds the allocators behind that, from Pony's C runtime (ponyc/src/libponyrt, commit cc2ec5d), on Rust's stable Allocator trait: a size-class pool owned per thread, a heap per actor, iso/val/tag as types, a lock-free mailbox, and a small scheduler to drive them.

1. The idea

An actor is a state, a mailbox and a heap, run by one thread at a time. Objects it allocates live in its heap. When it sends one to another actor, it sends the pointer. The object is freed later, by its owner, when nobody holds it any more.

 thread A (worker 0)                              thread B (worker 1)
 ┌ Producer actor ───────────────┐               ┌ Consumer actor ────────────┐
 │ heap (Local): free lists      │  send(Iso)    │                            │
 │   buf = Iso::new_in(.., heap) │ ────────────▶ │ mailbox ◀ pool-allocated   │
 │                               │   pointer     │   message node             │
 │ remote list ◀───────────────────────────────── drop(buf): remote free      │
 │   collect() after each batch  │   one CAS     │                            │
 └───────────────────────────────┘               └────────────────────────────┘
 pool (per thread): message nodes freed on B go back to A's inbox, 32 at a time

Two different "owners" are involved, just as in Pony: a heap block belongs to an actor, and a pool block (messages, chunks) belongs to the thread that carved it. Both are freed by whoever drops them and sent home to their owner in batches.

3. The pool: blocks owned by threads

C

Pony's pool has a thread cache, slabs inside 8 MiB arenas inside 256 MiB regions, and a long comment file (original/POOL_ARENA.md). The core is short. Allocation tries the cache, then the current slab, then the inbox of blocks other threads freed, then new memory:

Freeing finds the arena by masking the address (arena_of) and checks who owns it. Another thread's block is never put on this thread's lists; it goes onto a chain for its owner:

The owner takes its whole inbox with one atomic swap:

4. The per-actor heap

C

A Pony heap is a set of chunk lists per size class plus the GC threshold:

{{c-item original/heap.h typedef struct heap_t}} {{c-item original/heap.c void* ponyint_heap_alloc_small(}}

A chunk's bitmap marks free slots. Pony never frees one object at a time: the actor marks what it can reach between behaviours and sweeps the rest (ponyint_heap_endgc). Objects other actors hold survive because their reference counts are above zero (ORCA, section 9).

Rust: two handles

Rust frees objects one at a time, when they are dropped, and a sent object can be dropped by any actor on any thread. The heap therefore has two handles that share one Arc:

{{rs-item src/heap.rs pub struct Local}} {{rs-item src/heap.rs pub struct Remote}}
  • Local is !Send. It allocates and frees with plain free lists, no atomics. Because it cannot leave its thread, neither can any Box<T, Local> or Vec<T, Local> built on it.
  • Remote is Send + Sync and can only free: it pushes the block onto the heap's atomic remote list.
{{rs-item src/heap.rs unsafe impl Allocator for Local}} {{rs-item src/heap.rs unsafe impl Allocator for Remote}}

Between batches of behaviours, where Pony would GC, the actor takes the whole remote list at once:

{{rs-item src/heap.rs pub fn collect(&self)}}

This is the "message-passing free" of snmalloc, which came out of Microsoft's Pony-inspired Verona project. It is the same shape as the pool's inbox one layer down: an owner, a lock-free list others push onto, and a single swap to drain it.

The heap lives as long as any handle does. If an actor stops while one of its objects is still held elsewhere, the heap stays until that object is dropped (test heap_outlives_its_owner_while_objects_are_out). Pony gets the same effect from reference counts.

The crate docs carry three compile_fail tests that cargo test checks:

  • Using an Iso after sending it: E0382, use of a moved value.

6. The mailbox

C

The queue always keeps one consumed node, the stub. A push is one exchange on head. Bit 0 of head is set when the queue is empty and the actor is not scheduled, so a sender learns "I must schedule this actor" from the same exchange:

{{c-item original/messageq.c static bool messageq_push(messageq_t* q, pony_msg_t* first, pony_msg_t* last)}} {{c-item original/messageq.c pony_msg_t* ponyint_actor_messageq_pop(messageq_t* q)}} {{c-item original/messageq.c bool ponyint_messageq_markempty(messageq_t* q)}}

Rust

A line-by-line port. Nodes are Box<Node<M>, Pool> turned into raw pointers; the message is a MaybeUninit<M> so the stub holds nothing. The tag bit uses map_addr, which keeps the pointer's provenance.

{{rs-item src/queue.rs pub fn push(&self, msg: M)}} {{rs-item src/queue.rs pub unsafe fn pop(&self)}} {{rs-item src/queue.rs pub unsafe fn mark_empty(&self)}}

pop and mark_empty are unsafe: only one consumer may call them. The actor cell is that consumer, so user code never does.

Workers are threads with a command channel. spawn runs the actor's constructor on its worker, with its new heap, so the state can allocate there. Actors stay on that worker: Pony's schedulers steal actors from each other, but moving a Local to another thread would need an unsafe impl Send justified by "the state and its heap always move together". 8. How to use it

A producer fills buffers in its own heap and sends them as Isos; the consumer sums and drops them. The shared setting is a Val.

{{rs-item examples/demo.rs fn receive(&mut self, cx: &Context<'_, ProducerMsg>, msg: ProducerMsg)}} {{output pony_actors demo}}

Things to see in the output (exact numbers vary between runs, because the threads interleave differently):

  • The producer's heap stays at the same number of chunks every round. The consumer's drops come back as remote frees and are reused.
  • The first buffer's address shows up again in later rounds: the same block went out, came back and went out again.
  • The 4 KiB element arrays are pool blocks freed on the consumer's thread, so they return to the producer's thread in batches.

9. What is not ported, and why

  • ORCA, Pony's GC for objects shared between actors. Pony traces every message on send and receive and keeps per-actor reference counts, because its type system allows many references inside an actor and a GC must find them. In Rust, the owner of an Iso is known statically, and Val counts its own references, so a drop is enough.
  • Tracing inside an actor. Drop replaces it. Cycles of Vals leak, as with Arc.
  • Actor GC and the cycle detector. Actors live until System::shutdown. Dropping every Addr does not stop an actor.
  • Work stealing (section 7), backpressure (muting senders of an overloaded actor), and the pagemap, which Pony needs only to find an object's owner during tracing.
  • Collections. Only Box and Vec take an allocator on stable, and some Vec methods still don't: Vec::drain needs allocator_ext for a custom allocator. String and HashMap inside a state still use Global.

10. How it is checked

  • 14 tests in tests/pony.rs:
    • pool reuse and alignment;
    • 32 blocks freed on another thread coming back through one inbox batch;
    • heap accounting;
    • an Iso freed on another thread and reused at the same address;
    • Val shared by 4 threads and dropped exactly once;
    • mailbox empty-bit rules and per-sender order under 4 producers;
    • an actor running more than one batch;
    • Isos passing through three actors at the same address.
  • 3 compile_fail doc tests for the capability rules (section 5).
  • Miri runs the tests under 4 thread schedules (-Zmiri-many-seeds=0..4) and under Tree Borrows, and finds no undefined behaviour. Its only warnings are the expected integer-to-pointer casts from the slab lookup.
