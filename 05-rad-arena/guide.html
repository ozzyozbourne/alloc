RAD Debugger arena in Rust

The one allocator the whole RAD Debugger is built on: a stack of bytes backed by reserved virtual memory, which commits pages as it grows, chains new blocks when it fills up, and is freed by popping back to a saved position. This is the most complete port in the guide.

1. The idea

An arena is a linear allocator (folder 01) with three upgrades:

  1. It pops to any position, not just to zero. Save pos, do some work, pop back to pos. That is a stack, and it gives temporary memory scopes (Temp).
  2. It reserves address space, not memory. Each block reserves 64 MiB of address space, which costs nothing, and commits real pages in 64 KiB steps only as the position reaches them.
  3. It never runs out (until the OS does). When a block's reservation is full, it reserves another block and links it to the previous one. Positions keep counting across blocks.
 block 1 (reserve 64 MiB)                                block 2 (chained)
 ┌────────┬──────────────────────┬──────────┬─────────┐   ┌────────┬───────────┬──────────────┐
 │ header │  allocations ...     │ committed│ reserved│ ← │ header │ alloc ... │   reserved   │
 │ 128 B  │                      │  unused  │ only    │   │ 128 B  │           │              │
 └────────┴──────────────────────┴──────────┴─────────┘   └────────┴───────────┴──────────────┘
          base_pos = 0                                     base_pos = 64 MiB     ^ current->pos
 arena_pos() = current->base_pos + current->pos      (one number across the whole chain)

RAD's style is to give every kind of data a lifetime and an arena with that lifetime: one per view, one per frame, one per debug-info load. When the lifetime ends, the whole arena is popped or released at once. There is no per-object free and no general heap, and in the C code that removes whole classes of leak and double-free bugs.

2. The C version

Types

The Arena struct is also the header of each block: arena->current is the block being filled, and each block links to the previous one with prev.

Reserve, commit, release

On Linux these are thin wrappers around mmap with PROT_NONE (reserve address space), mprotect to read/write (commit), and munmap (release).

Creating an arena

Rounds the sizes to pages, reserves, commits the first part, and writes the header into the first 128 bytes. Most of the length is the optional global debug table.

Pushing

Align the position; if it does not fit in this block, chain a new one (or reuse one from the free list); commit pages if needed; return the pointer and optionally zero it. Out of memory aborts the process, so callers never see a null pointer.

Popping and temp scopes

Popping releases whole blocks above the target position, then moves the position inside the remaining block. temp_begin/temp_end just save and restore a position.

Like every arena in C, nothing stops code from keeping a pointer across temp_end. RAD relies on conventions and ASan poisoning (the AsanPoisonMemoryRegion calls) to catch that.

3. The Rust version

Reserve, commit, release

Same system calls through the libc crate. On non-Unix targets, and under Miri, which cannot run mmap, a fallback allocates each block up front from System.

Types

The block header is a separate Block struct written at the start of each block, as in C. The Arena value you hold is a small handle with the current block (in a Cell, since allocate takes &self) and the settings used for new blocks. A compile-time assertion checks the header fits in 128 bytes, the same as C's StaticAssert.

Pushing

The same three steps as arena_push: fit in the current block, otherwise chain a block big enough for the request, then commit pages up to the new end. Every failure returns AllocError.

Popping

pop_to, pop and clear take &mut self. Anything allocated from the arena holds a shared borrow, so the compiler rejects a pop while any of it is still in use. That replaces ASan as the guard against use-after-pop, at compile time and in release builds:

Temp scopes

Temp holds &mut Arena and the saved position, and pops back in Drop. It dereferences to Arena, so you allocate from it directly, and scopes nest with temp.temp(). Because it borrows the arena mutably, nothing outside the scope can use the arena while the scope is open, and nothing allocated inside can outlive it.

Implementing Allocator

Beyond the required two methods, the arena overrides grow and shrink. A Vec that is the most recent allocation can grow in place by moving the top up, so pushing to it never copies. deallocate also reclaims space when you free the most recent allocation, which makes short-lived Boxes free. Anything else waits for a pop.

C-style helpers

push, push_slice and push_str mirror push_array and push_str8_copy. They return &mut T from &self, which is sound because each push returns fresh memory no one else can reach. Values pushed this way are never dropped, as in C; use Box::new_in when a destructor must run.

5. How to use it

Inside the scope, 1,000 symbols with their names used about 57 KB; dropping the scope returned the arena to 152 bytes (the 128-byte header plus the module name and base address). Pushing 1.5 MB into 1 MB blocks chained a second block, and pop_to released it. The last line shows a Vec growing to 10,000 elements without ever moving, thanks to the in-place grow.

6. Building it yourself, step by step

  1. Write the OS layer: reserve (mmap(PROT_NONE) / VirtualAlloc(MEM_RESERVE)), commit (mprotect / VirtualAlloc(MEM_COMMIT)), release.
  2. Put a header at the start of each block with its position, committed size, reserved size, the previous block, and its base_pos.
  3. Write push: align, chain if past the reservation, commit if past the committed size, bump.
  4. Write pop_to(&mut self, pos): release blocks whose base_pos is at or above pos, then set the position in the block that is left.
  5. Add a Temp guard holding &mut Arena that pops in Drop.
  6. Implement Allocator: allocate calls push; override grow to extend the top allocation in place.
  7. Test chaining with a small reserve, lazy commit, nested temps, an oversized push, and in-place growth. Run under Miri using the System fallback.
