Kohi linear allocator in Rust

A bump allocator over one block of memory. The C version is about 60 lines. This page shows it, the Rust port built on std::alloc::Allocator (stable in Rust 1.100), and how the two compare.

1. The idea

A linear allocator owns one block of memory and an offset into it. Allocating returns the address at the offset and moves the offset forward by the requested size. Single allocations are never freed. Instead, free_all moves the offset back to 0, which frees everything in one step.

 block (total_size bytes)
 ┌──────────┬──────┬────────────────┬──────────────────────────────┐
 │  alloc 1 │ pad  │    alloc 2     │            free              │
 └──────────┴──────┴────────────────┴──────────────────────────────┘
 ^ memory                           ^ memory + allocated             ^ memory + total_size

 allocate(n):  p = memory + allocated;  allocated += n;  return p
 free_all():   allocated = 0

This makes allocation a few instructions with no per-allocation bookkeeping. The cost is that you must know when everything in the block is finished, for example at the end of a frame. Kohi uses it for per-frame and startup data.

The pad in the diagram only exists in the Rust version. The C version never pads, which is its main problem (see section 5).

2. The C version

The state is four fields. owns_memory records whether the allocator allocated the block itself or was handed one.

Creating it either uses a block you pass in or allocates one through kallocate, Kohi's engine-wide allocator (folder 04).

Allocating checks for space, returns the current position and moves it forward. There is no alignment parameter.

Freeing everything resets the offset, and optionally zeroes the whole block.

Nothing in C stops you from calling free_all and then reading a pointer you got before it. The next allocation will overwrite that data.

3. The Rust version

The struct

Same fields, with two changes. allocated is a Cell, because Allocator::allocate takes &self: many Vecs and Boxes share one allocator through shared references, so the allocator has to change its own state through &self. And a lifetime parameter 'buf ties the allocator to a borrowed buffer, so the buffer cannot be freed while the allocator uses it.

Creating it

C's single create with an optional memory pointer becomes two constructors. new owns its block; from_buffer borrows one, such as a stack array.

Implementing Allocator

This is the whole allocator. Only two methods are required; grow, shrink and allocate_zeroed have default implementations built on these two.

Three things to notice:

  • Alignment. The start is rounded up to layout.align(). It rounds the address, not the offset, so it is right even when the buffer itself is misaligned.
  • Overflow. checked_next_multiple_of and checked_add return None on overflow, which becomes AllocError. The C version computes allocated + size without checking.
  • Return type. NonNull<[u8]> is a pointer plus a length. The length tells the caller how many bytes it actually got, which can be more than it asked for (the pool in folder 02 uses this).

Resetting it

The important part is &mut self. Every Vec<T, &LinearAllocator> holds a shared borrow of the allocator, and the compiler will not let you take &mut while any shared borrow is alive. So you cannot reset the block while anything still points into it:

Destroying it

C's linear_allocator_destroy becomes Drop, so it runs automatically and only once.

5. The alignment problem in the C version

C: allocations are packed back to back. Allocate 1 byte, then a u64, and the u64 lands at an odd address. On x86 that is only slower; on some ARM targets, and for SIMD types, it faults or is undefined behaviour.

The Rust test aligns_each_allocation_unlike_the_c_version checks the fix: a u8 followed by a u64 uses 16 bytes (1 + 7 padding + 8), and the u64 address is a multiple of 8.

6. How to use it

Pass &allocator as the last argument of any *_in constructor. &A is itself an Allocator when A is, so many containers can share one allocator.

Watch out for growing Vecs. When a Vec outgrows its capacity, the default grow allocates a new buffer and copies; the old buffer is not reclaimed until free_all. Reserve the capacity you need up front. The RAD arena (folder 05) overrides grow to extend the last allocation in place.

7. Building it yourself, step by step

  1. Pick the state. A pointer to the block, its size, and a Cell<usize> offset. Use Cell because allocate only gets &self.
  2. Get a block. Global.allocate(Layout::from_size_align(size, 16)?), and remember the layout so Drop can free it with exactly the same one.
  3. Write allocate. Round the current address up to layout.align(), add layout.size(), check against the end, store the new offset, return NonNull::slice_from_raw_parts(ptr, size). Use checked arithmetic and return Err(AllocError) on any failure. Never panic: the trait requires that allocator methods do not unwind.
  4. Write deallocate as an empty function.
  5. Write the unsafe impl with a // SAFETY: comment that explains why blocks never overlap and stay valid until they are invalidated. Implementing Allocator is unsafe because collections trust these promises.
  6. Make reset take &mut self. This is what turns use-after-reset into a compile error.
  7. Test it with values of different alignments, exhaustion, and reuse after reset. Run the tests under Miri (cargo +nightly miri test) to catch undefined behaviour in the unsafe code.

8. Tests

tests/linear.rs checks alignment (including inside a deliberately misaligned buffer), exhaustion, free_all reusing and clearing the block, and that deallocate keeps memory. All pass on Rust 1.100 beta and under Miri with -Zmiri-strict-provenance.
